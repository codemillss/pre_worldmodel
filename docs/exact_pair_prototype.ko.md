# 검증 수준을 유지한 비교 처리 최적화: 저장 자료 대조

2026-10-28 · 저장 자료 대조 완료 · 원본·판정 보존 통과 · **실험 실행기에 적용하지 않은 시제품**

## 1. 로봇 성능을 유리하게 바꾸는 작업인가

아니다. 이번 질문은 **이미 저장된 같은 결과를 같은 기준으로 검사하면서, 반복 순회의 처리 시간을 줄일 수 있는가**다. 모델 가중치·자료·비용식·행동 후보·성공 기준을 바꾸거나 실패를 성공으로 다시 분류하지 않았다. 새로운 물리 궤적·모델 예측·학습 갱신은 모두 0회다.

목적은 [목표 근처에서 같은 후보의 예측과 실제 미래를 비교하는 진단](nt_fullbank_execution.ko.md)을 진행할 자원을 확보하는 것이다. 원래 정식 결과와 70/768회에서 멈춘 후속 실행은 그대로 남겼다. 698회는 여전히 미실행이며, 모델·비용·후보 탐색 중 무엇이 최종 실패를 일으켰는지는 이번 작업으로 밝혀지지 않는다.

## 2. 무엇을 바꿨는가

[직전 비용 분해](nt_storage_profile.ko.md)에서 느린 후보11/B의 전체 결과 보존 묶음 중 약71.86%가 네 번의 exact 비교에서 발생했다. 이 비중은 해당 저장 사례의 관찰이며 전체 후보의 고정 비율이 아니다.

기존 비교는 왼쪽 타입 트리의 SHA, 오른쪽 SHA, 직접 동등성을 별도로 순회해 계산한다. 새 [시제품](../src/push_align/exact_pair_prototype.py)은 형태가 맞는 두 트리를 함께 순회하면서 **양쪽 SHA와 직접 값·타입·비트 비교를 모두 수행**한다. 구조가 다르거나 지원하지 않는 입력은 기존 검사 경로로 처리한다.

해시가 같다는 이유만으로 같다고 판정하지 않는다. 비교 결과의 schema·문구·두 SHA도 기존과 같아야 한다. 진단 자료의 기존 JSON 정규화 규칙, 숫자 배열의 dtype·shape·바이트와 스칼라 비트, 상태·판정 필드도 유지한다. 원래 함수·저장 형식·실행기에는 적용하지 않았다.

전체 결과 묶음의 아래 네 비교도 그대로 유지했다.

1. 저장 함수 안의 자기 비교.
2. 재읽기 함수 안의 자기 비교.
3. 저장 전후 전체 필드 트리 비교.
4. 복원한 전체 `FollowupProbe` 객체 비교.

따라서 이번 개선은 검사 횟수나 필드를 줄인 효과가 아니다. 직접 비교 기준은 해시 결과와 별개로 남겼지만, 구현의 오류 가능성이 없어졌다는 의미는 아니다.

## 3. 작은 대조의 설계와 결과

실행 전에 [설정 v1](../configs/exact_pair_prototype.v1.json)을 남기고, 독립 코드 검토에서 종료 시 새 코드·설정 재인증과 손상 자료의 같은 거부 결과를 추가한 [v2](../configs/exact_pair_prototype.v2.json)로 등록했다. 변경은 시간 측정 전에 이뤄졌으며 v1도 보존했다.

대상은 기존 N-T의 기본 후보0/A와 느린 후보11/B다. 각 사례를 기존·시제품으로 각각3회 처리했다. 순서는 기존→시제품, 시제품→기존, 기존→시제품이다. 매번 새 폴더에 저장해 모든 출력과 느린 반복도 보존했다. 원본을 인증·읽은 이후의 **캐시가 데워진 조건**이며, 미실행 후보의 최악 시간을 측정한 실험이 아니다.

### 전체 결과 저장·재읽기·복원·네 비교

| 저장 사례 | 기존 중앙값 | 시제품 중앙값 | 처리 시간 감소 |
|---|---:|---:|---:|
| 후보0/A | 2.691081초 | 1.354796초 | 49.66% |
| 후보11/B | 6.181079초 | 3.522732초 | 43.01% |

12개 묶음의 모든 NPZ·gzip 출력, 총24개 파일이 해당 원본 저장 파일과 바이트 단위로 같았다. 각 묶음의 네 비교 결과도 두 구현에서 정확히 같았다. 최적화된 모듈을 기존 코드의 별도 메모리 사본에만 연결했으며 원래 함수 바인딩은 변하지 않았다.

### 저장된 마지막 행동 구간의 직접 비교만 분리 측정

| 저장 사례의 마지막 `StepResult` | 기존 중앙값 | 시제품 중앙값 |
|---|---:|---:|
| 후보0/A | 0.110691초 | 0.041727초 |
| 후보11/B | 0.159607초 | 0.062248초 |

이 표는 서로 독립적으로 읽은 같은 행동 구간의 **exact 비교만** 측정한 것이다. 물리 실행·구간별 raw 저장·인증·재읽기를 포함한 전체 구간 단가가 아니다. 전체 결과 표와 더해 새 실행기의 시간을 계산해서는 안 된다.

외부 프로세스 실측은 **49.786781초**다. 원본 인증·읽기, 모든 묶음·구간 비교·손상 검사와 종료를 포함하며, 코드 작성·앞선 단위검사·별도 독립 감사·문서 시간은 포함하지 않는다. 이 시간들은 아래 전체 작업 시계에 들어가므로 자식 타이머를 다시 더하지 않았다.

## 4. 더 빨라진 대신 놓치는 값이 생기지 않았는가

- [계약 검사14개](../artifacts/validation/exact_pair_contract_tests.v1.json)가 통과했다. 스칼라 비트·배열 dtype/shape/바이트·중첩 자료·기존 진단 정규화·지원하지 않는 타입을 대조했다.
- **같은 SHA를 갖지만 실제 dataclass 타입이 다른 값**과 tuple 하위 타입 사례를 두 구현 모두 거부했다. 해시만 보는 구현으로 대체되지 않았는지 확인하는 검사다.
- [독립 감사](../artifacts/validation/exact_pair_independent_review.v1.json)는 실제 후보11/B의 마지막 구간에서 행동1비트, 진단 실수1비트, 판정 bool→int의 세 변형을 만들었다. 두 구현 모두 같은 `FAIL_EXACT` 결과를 냈다.
- 별도 복제 파일을 손상시킨4건도 같은 예외 타입·문구로 거부했다. 손상 복제본을 원본에 덮어쓰지 않았고 그대로 보존했다.
- 원래 추적 파일1,641개와 두 원본 실행의759개 파일을 해시 대조해 보존을 확인했다. 모델·정규화·기존 설정·코드·보고서가 이 범위에 포함된다.

이는 선택한 저장 사례와 경계 조건의 검사다. 모든 Python 객체에 대한 형식적 동등성 증명이나 전체 프로젝트 회귀검사를 대신하지 않는다. 독립 감사의 검사 항목 수도 새로운 실험 표본 수가 아니다.

## 5. 남은698회를 지금 실행할 수 있는가

**아직 재개하지 않는다.** 시제품의 전체 실행기 단가는 `NOT_CALIBRATED_NOT_RUN`이다. 전체 결과 묶음이 빨라졌다는 사실과 실제 실행 전체가2시간에 들어온다는 판단은 구분한다.

[자원 재검산 v1](../artifacts/validation/exact_pair_resource_review.v1.json)은 기존 최대 단가와 안전계수를 유지했다. 종전 장부51.0349분에 이번 작업 시계와 시계 시작 전의 보수적180초 여유를 더한 판정 시점 누적은60.6245분이었다. 그 조건에서 **기존 실행기의 예상 총량은168.0486분으로 계속 보류**다. 이는 새 시제품을 적용한 실행기의 예상 시간이 아니다.

외부 프로세스49.7868초는 전체 작업 시계의 일부로 한 번만 계상했다. 준비·검사·대기·감사를 포함한 경과 시간에 다시 더하지 않았다.180초는 측정한 시간이 아니라 명시적으로 남긴 보수적 여유다. 이 자원 기록 이후의 문서·검산 시간은 다음 진입 검사에서 추가 계상해야 한다.

두 사례의 빠른 중앙값으로 기존 관측 최대값을 낮추거나, 기존 중단을 소급 취소하지 않았다. 실제 구간의 물리·raw 저장·복원·재현 비교와 새 이어받기 실행기의 고정 비용을 별도로 재야 전체 예산을 판단할 수 있다.

## 6. 다음에 확인할 가장 작은 작업

시제품은 저장 자료의 대조를 통과했으나 아직 실험용 실행기에 승격하지 않는다. 다음은 **같은 저장된 구간의 전체 raw 저장→인증·재읽기→직접 비교 경로**를 기존·시제품으로 처리해, 비교 이외의 비용까지 유지되는지 확인하는 것이다. 원본 출력 바이트와 변형 거부도 다시 대조한다.

그 뒤 필요한 실행기 사전 검사와 자원 재검산을 통과해야 미실행 후보를 이어받을 수 있다. 원래 모델의 정렬 성능을 높이거나 유리한 결과를 고르는 작업과는 목적·판정·증거를 분리한다.
