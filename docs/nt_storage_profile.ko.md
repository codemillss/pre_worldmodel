# 전체 결과 저장·복원 비용 분리 측정과 잔여 실행 판단

2026-10-22 · 저장 자료 계측 완료 · **남은 698회 실행은 자원 보류**

## 1. 무엇을 확인했는가

N-T 전체 실행이 [70/768회에서 중단](nt_fullbank_execution.ko.md)됐을 때 후보11/B/첫 반복의 `first_repeat_complete_probe_durable_roundtrip`은 6.159초였다. 이 이름만으로 디스크 저장이 느려졌다고 판단할 수 없다. 실제 구간은 전체 필드 트리 생성 → 저장 → 인증·재읽기 → 트리 비교 → `FollowupProbe` 객체 복원 → 객체 비교 → 영수증 저장을 포함한다.

이번에는 **같은 원시 내용·같은 저장 형식·같은 검증을 유지하며 어느 처리 구간이 비용을 차지하는가**를 확인했다. 새 실제 궤적이나 모델 예측을 만들지 않았다. 기존 중단 상태와 698건 미실행 판정도 유지했다.

## 2. 어떻게 측정하고 같은 검증을 보장했는가

[고정 설정](../configs/nt_storage_profile.v1.json)의 여섯 저장 사례를 각3회 처리했다. 후보0의 A/B는 기본 비교, 후보9/B는 0.6초 조기 준비 사례, 후보11의 A/B는 비용 증가 구간, 후보127/B는 앞선 사전 검사의 다른 긴 사례다. 후보127은 이번 70회 본 실행의 결과로 섞지 않았다.

원래 함수의 소스 트리를 별도 메모리에 복제하고 시간 측정 문맥만 삽입했다. 타이머를 제거하면 원래 구문 트리와 정확히 일치해야 한다. 실행된 원래 코드 파일·함수 바인딩·학습 가중치를 바꾸지 않았다. 압축·fsync·외부/내부 해시·전체 dtype/shape/비트·스칼라 타입·튜플/리스트·중첩 진단을 그대로 처리했다.

저장 함수 안의 자기 비교, 읽기 함수 안의 자기 비교, 저장 전후 트리 비교, 복원한 전체 객체 비교의 **네 exact 비교를 모두 유지**했다. 각 비교는 typed hash 두 개와 직접 재귀 동등성 검사를 포함한다. 해시만 확인하는 방식으로 바꾸지 않았다.

- 계측18회와 별도로 후보11/B를 원래 함수로3회 처리했다. 전후 순서를 번갈아 배치하고, 계측판과 원래 함수의 NPZ·gzip 파일 SHA가 같아야 통과하도록 했다.
- 독립 감사는 21개 새 파일 쌍 모두가 해당 원래 저장 사례와 바이트 단위로 같음을 확인했다. 새 경로를 담은 영수증 자체는 별도 파일이다.
- 모든 출력은 새 폴더에 배타적으로 저장하고 보존했다. 원래 두 실행의 **759파일** 목록·해시도 변하지 않았다.
- 중첩 타이머의 부모 시간은 자식 시간과 겹친다. 각 사례에서 **배타적 시간 합 = 전체 시간**을 벽시계·CPU 시계 각각 검사했다.
- 중첩 합산·비트/타입 보존·손상 파일 거부 계약 검사3개, 자원 산식 검사9개가 통과했다. 새 물리·환경 구성·모델 호출 감시10종은 모두0회였다.

원래 자료를 인증·읽은 뒤 계측했으므로 **캐시가 데워진 파일시스템 조건**이다. 압축과 쓰기, 압축 해제와 파싱이 묶인 구간을 순수 디스크 지연으로 부르지 않는다. 초기 인증·구문 트리 계측 준비·대조 실행·마지막 재해시도 외부 프로세스 시간에는 포함했다.

후보11/B는 이번 계측에서도 6.125–6.240초였다. 원래 함수 대조는 **6.429·6.140·6.117초**였고 압축 파일 내용은 같았다. 가장 느린 새 관측값6.429초는 원래 함수에서 나왔으므로 계측 오버헤드라는 이유로 빼지 않았다. 계측/원래 함수 비율은 0.971·1.001·1.001이며, 이를 정확한 오버헤드 추정치로 해석하지 않는다.

## 4. 확인된 원인과 남은 가설

**확인한 사실:** 후보11/B의 큰 처리 비용은 같은 저장 내용으로 재현된다. 그 비용 대부분은 exact 검증과 타입 트리 처리에서 발생한다. 같은 물리 구간 수라도 진단 내용의 크기가 다르다. 따라서 기존의 전체 묶음 비용을 모두 저장·읽기 속도 문제로 해석하던 설명은 수정한다.

**아직 확인하지 못한 것:** 과거6.159초가 측정됐던 순간의 OS 부하·캐시·메모리 회수·발열 조건은 기록이 없어 판별할 수 없다. 접촉 기록 수만을 독립적으로 바꾼 실험도 아니므로 접촉 수가 지연을 얼마나 일으켰는지 인과 계수로 제시하지 않는다. 이번 결과는 작업량과 실제 처리 경로의 병목을 좁힌 것이다.

타입 복원 객체 생성 자체는 수십 마이크로초지만, 그 앞의 중첩 트리 디코딩과 네 번의 exact 검증은 크다. 파일 압축률만 바꾸거나 영수증을 줄이는 작업을 우선 개선책으로 삼기에는 현재 근거가 부족하다.

## 5. 누적2시간 안에 남은 실행이 가능한가

**현재 코드·기존 최대값 정책으로는 재개 보류다.** [최종 자원 검산](../artifacts/validation/nt_storage_profile_resource_final.v1.json)은 완료70회와 정확한 미실행 키를 인증하고 아래 수량만 계산했다.

| 남은 작업 | 수량 |
|---|---:|
| 새 실제 궤적 | 698회 |
| 최악의 행동 구간 | 4,540구간 |
| 원본 D2와 raw 대조 | 26회 |
| 첫 반복 전체 결과 저장·복원 | 232그룹 |

기존 최대 구간 단가0.516129초, 원본 대조1.357066초, 루프0.026951초를 유지했다. 전체 결과 묶음은 기존6.158993초와 이번21회 관측 최대6.429130초 중 큰 값을 사용했다. 시간·저장 안전계수1.5, 최종 정리600초, 반환 구간 봉인60초, 저장5GiB·여유2GiB 조건도 유지했다. 구간 봉인 여유는 원래 별도 검사로 유지하며 전체 예산에 중복 합산하지 않았다.

이전 전달 장부의 감사·정리·게시 여유까지 포함한 보수적 누적 **1,736.593초**를 출발점으로 삼았다. 이번 프로파일 외부 실측 **104.868초**, 겹치지 않는 준비·사후 시간을 더했다. 타이머 내부 단계·반복·독립 감사의 개별 소요는 이 경과 시간에 다시 더하지 않았다. 단가 재검산은 사후 게시120초까지 보수적으로 계상한 51.03분을 출발점으로 삼았다. 준비 시간은 계측 코드 파일 생성부터 실행 시작까지, 사후 시간은 프로파일 종료부터 검산 시점까지의 경과 시간으로 측정했다.

- 앞으로 필요한 시간: 기존 최대값 유지 **105.86분**, 새 최대값 반영 **107.42분**.
- 현재 누적과 남은 작업 합계: 기존 단가 **156.89분**, 새 최대값 반영 **158.46분**.
- 새 최대값 반영 시2시간 상한 초과: **38.46분**.
- 저장·디스크 여유: 모두 통과(검산 당시 누적 저장 예상 약1.04GiB; 시간 조건만 보류).

이번 프로파일 비용을 빼도, 이전 전달 시점에서 같은 최대값 정책의 잔여 전체 예상은 이미 약134.8분이었다. 이번 분석 때문에만 재개가 불가능해진 것은 아니다. 반대로 빠른 반복의 평균을 골라 기존 최대값을 낮추는 방식으로 진입을 통과시키지도 않았다.

선별 공개 자료에는 첫 검산154.27분의 수치도 보존했다. 위 최종 검산은 그 이후의 감사·정리 시간까지 다시 계상한 것이며, 두 장부를 중복해서 더하지 않았다.

이는 **원래70회를 그대로 보존하고 미실행698회만 이어받을 수 있다고 가정한 산식**이다. 별도 이어받기 실행기의 검증·참조 복원 비용까지 실측한 실행 승인은 아니다. 추가 진입 비용이 생기면 더 늘어날 수 있다. 기존 중단 실행을 완결768회 실험으로 바꾸지 않는다.

## 6. 다음에 확인할 가장 작은 행동

다음 개선 대조의 우선 대상은 **같은 타입·비트·전체 필드·해시와 직접 동등성 검사를 더 빠르게 수행하는 구현**이다. 후보11/B와 기본 사례의 저장 내용으로 기존 구현과 새 구현을 대조하고, 전체 필드 일치와 손상·변형 거부가 그대로인지 먼저 확인해야 한다. 비교 횟수나 진단 필드를 줄이는 것은 이번에 검증한 개선이 아니다.

이번에는 최적화 코드를 적용하거나 남은698회를 실행하지 않았다. 더 빠른 구현이 입증되더라도 새 버전·작은 사전 측정·전체 남은 자원 재검산이 필요하다. 이 결과만으로2시간 내 완료를 보장하지 않는다.
